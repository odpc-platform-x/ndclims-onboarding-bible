    Section 1 · Super Admin

    ตั้งค่าแล็บใหม่

    ลำดับบังคับที่ระบบ reject ถ้าข้ามขั้น

    ลำดับบังคับ

    global roles (มากับ migration, company_id IS NULL) └→ company + สาขา HQ + admin — transaction เดียว └→ plan / entitlements └→ test catalog └→ departments & specimen types └→ referring orgs └→ users / patients └→ integrations

    POST /api/super-admin/companies

    สร้าง company + branch code HQ (isMainBranch=true) + admin user ในtransaction เดียว. ต้องมี role row code company_admin, company_id IS NULL อยู่ก่อนแล้ว ไม่งั้น fail

    uniqueness เงื่อนไข ผลถ้าซ้ำ
    companies.code uppercase ก่อนเทียบ 409
    companies.subdomain lowercase ก่อนเทียบ 409
    ไม่มีคำสั่งสร้าง super_admin คนแรก. DB ที่ไม่ได้ seed มี super_admin = 0 คน และไม่มี HTTP path สร้างได้เลย — ต้องมาจาก SQL seed หรือ manual INSERT. อย่าลบ super_admin คนสุดท้ายทิ้ง

    plan / entitlements / catalog

    PATCH /api/super-admin/companies/:id/plan
PUT   /api/super-admin/companies/:id/features/:key

    POST /api/super-admin/catalog/publish — ดันชุดตรวจ DDC จากส่วนกลางลงบริษัท. ไม่ใส่ companyIds = ทุกบริษัท active ที่ไม่ถูกลบ. สร้าง lab_test_categories จาก categoryCode ให้อัตโนมัติถ้ายังไม่มี และอัปเดตเฉพาะ ฟิลด์โครงสร้าง — ราคา, ต้นทุน, สถานะเปิดปิด, ลำดับ ไม่ถูกแตะ ปลอดภัยต่อการรันซ้ำ 

    POST /api/super-admin/catalog/import-from-company   # harvest จาก tenant เดียวขึ้นส่วนกลาง

    route super-admin อื่น: GET /stats, GET/PATCH /companies/:id, GET /features, GET /companies/:id/entitlements, GET /monitoring/overview, GET /companies/:id/export, GET /users

    กับดัก

    company ใหม่มีแคตตาล็อกว่างเปล่า. ไม่มีแผนก ไม่มีชนิดสิ่งส่งตรวจ ไม่มีหมวดหมู่ ไม่มีรายการตรวจ ไม่มี settings — ไม่มีอะไร provision ให้เกินกว่า company/branch/admin
    Section 2

    หนุนงาน import ของผู้ใช้

    ผู้ใช้ทำเอง IT รู้ endpoint และข้อจำกัดไว้แก้ปัญหา

    Endpoint

    GET  /api/import/template/:entity   # .xlsx หัวตารางไทย + แถวตัวอย่าง
POST /api/import/:entity            # multipart upload

    entity ที่มีจริง: users, patients, lab-tests, packages, lab-orders — ไม่มีอื่น

    ทั้ง plugin อยู่หลัง feature gate import และต้องมีสิทธิ์ settings.manage

    ข้อจำกัด

    เงื่อนไข ค่า
    ไฟล์ .xlsx เท่านั้น (mimetype spreadsheetml.sheet / ms-excel / octet-stream หรือชื่อไฟล์ลงท้าย .xlsx)
    sheet อ่านชีตแรกเท่านั้น
    mapping ข้าม header row แล้ว map คอลัมน์ตามตำแหน่ง — สลับคอลัมน์ = ข้อมูลพังเงียบๆ
    แถวสูงสุด 5,000 แถว/ไฟล์
    การประมวลผล synchronous, ไม่มี job queue, ไม่มี progress, ไม่มี resume
    rollback ไม่มี — partial success ไม่ rollback แถวที่ error

    ลำดับบังคับ: patients ก่อน lab-orders (order resolve patient จาก HN)

    lab-orders specifics

    • order number มินต์เป็น IMP{yy}{mm}{dd}{seq} และ lsn = orderNumber — เลขที่เดิมของระบบเก่าไม่ถูกเก็บไว้
    • status มาจากวันที่ที่ให้มา: มี received date ⇒ processing, มี collected date ⇒ collected, ไม่มีทั้งคู่ ⇒ pending
    • string วันที่แบบไม่มีเวลา anchor เป็นเที่ยงคืน Bangkok ไม่ใช่ UTC
    • sending_org_code ที่ไม่ตรงกับหน่วยงานที่มี ไม่ทำให้แถวล้ม — เก็บเป็น snapshot string เฉยๆ ต้องเช็ครหัสหน่วยงานผิดด้วยมือ
    ห้ามรัน import สองไฟล์พร้อมกัน. การมินต์เลข order ทำ COUNT(*) ต่อแถว รันขนานกัน = เลขชนกัน. และเป็น O(n) query ต่อไฟล์ ไฟล์ใหญ่ช้า — ปรับ timeout ที่ proxy/nginx ด้วย

    ก่อนรัน / กู้พัง

    snapshot database ก่อน bulk import ทุกครั้ง — ไม่มี undo

    กู้ import ที่พังกลางทาง: แก้เฉพาะแถวที่ error แล้วอัปโหลดใหม่เฉพาะแถวนั้น ห้ามอัปทั้งไฟล์ซ้ำ — จะได้แถวที่สำเร็จแล้วซ้ำอีกชุด

    Section 3

    Integration

    ต่อทีละขั้น แต่ละขั้นพึ่งขั้นก่อนหน้า

    1 · referring organization

    GET /api/mophealth-facilities — directory NHSO กลาง PK hcode ~57k แถว โหลดโดย CLI script apps/backend/src/scripts/import-nhso-facilities.ts ไม่ใช่ migration 

    POST /api/referring-organizations   # adopt facility เข้า tenant

    2 · external lab config

    POST /api/external-lab-configs — ออก API key รูปแบบ ndcl_<48 hex> โชว์ครั้งเดียว เก็บแค่ SHA-256 hash ใน integration_credentials

    config มี allowedTests[] (บังคับเป็น scope — test นอก scope ⇒ 403), defaultBranchId, resultCallbackUrl, resultCallbackSecret (encrypted)

    ต้องมี referring organization อยู่ก่อน. ฟิลด์ identity ของ org ถูก snapshot มาจากมัน ไม่ได้พิมพ์เอง

    3 · partner push orders

    POST /api/public/v1/orders/structured
POST /api/public/v1/orders/batch   # สูงสุด 100 orders, คืน 202
POST /api/public/v1/orders          # legacy

    auth: header x-api-key ไม่ใช่ JWT. rate limit ต่อ key ต่อชั่วโมงผ่าน Redis (PUBLIC_API_RATE_LIMIT_PER_HOUR, default 1000) 

    GET /api/public/v1/orders/:submissionId/status
GET /api/public/v1/results/:orderId
GET /api/public/v1/results/lsn/:lsn

    Swagger สำหรับ partner: GET /api/public/docs, GET /api/public/openapi.json

    บังคับให้ partner ส่ง externalSubmissionId ทุกครั้ง. นี่คือ idempotency key — ถ้าไม่ส่ง retry จะสร้าง order ซ้ำ

    attachment: base64-inline, เพดาน 10 MB/ไฟล์ (server-side), สูงสุด 20 ไฟล์/order — ยังไม่มี external blob storage. เจ้าหน้าที่อ่านที่ GET /api/incoming-orders

    4 · instrument (agent)

    on-prem agent (apps/agent) ทำหน้าที่ decode ASTM/HL7 แล้ว post JSON ที่ normalize แล้ว 

    POST /api/instruments/agent/auth
POST /api/instruments/agent/heartbeat
POST /api/instruments/agent/results
GET  /api/instruments/agent/orders/:sampleId   # host query / worklist
    ผล map เข้ารายการตรวจผ่าน lab_tests.hl7_code (uppercase). ถ้าฟิลด์นี้ว่างหรือผิด ผลหายเงียบๆ ไม่มี error

    route จัดการ + device API key อยู่ที่ /api/instruments หลัง feature gate instruments

    5 · HL7

    POST /api/hl7/orders   # ORM^O01 v2.5 outbound
GET  /api/hl7/results/:id
GET  /api/hl7/messages
    ทางเดียว — outbound เท่านั้น. ไม่มี inbound ORU parser, ไม่มี MLLP listener, ไม่มี ACK handling. timestamp format เป็น UTC ไม่ใช่ local time. ตาราง hl7_messages เข้าถึงด้วย raw SQL — ไม่อยู่ใน Drizzle schema

    6 · webhook

    GET  /api/webhook-deliveries
POST /api/webhook-deliveries/:id/retry
POST /api/webhook-deliveries/run-retry-wave

    Feature gating เป็นจริงแบบนี้

    • integrations และ napplus — plan full เท่านั้น
    • instruments และ hl7 — ต้อง standard หรือ full
    • แล็บ trial ต่ออะไรไม่ได้เลยสักตัว
    Section 4

    Ops ระบบ live

    รักษาระบบให้รอด ไม่ใช่ตั้งค่าใหม่

    Schema migrations

    tree จริงคือ supabase/migrations/ (~69 ไฟล์) รันอัตโนมัติตอน backend boot ผ่าน apps/backend/src/lib/migrate.ts ติดตามใน schema_migrations table, 1 transaction ต่อไฟล์, เรียงตามชื่อไฟล์

    scripts/apply-migrations.sh — standalone runner (มี --dry-run, idempotent) สำหรับ deploy แบบ serverless ที่ boot-time migration ไม่รัน

    อย่าชี้ migration runner ไปที่ transaction-mode pooler. ใช้ DIRECT_DATABASE_URL
    DEAD PATHS — กับดัก: pnpm db:seed ชี้ไป packages/db/migrations/001_ndclims_schema.sql และ make migrate ชี้ไป database/ ที่ไม่มีอยู่จริง — ทั้งคู่ไม่ใช่ tree จริง ใช้ setup-local-db.sh หรือ boot-time runner เท่านั้น

    Backup / restore / rollback

    ดู DEPLOYMENT.md §8 สำหรับขั้นตอนเต็ม

    backup ที่ไม่เคย restore ไม่นับว่าเป็น backup
    migration ที่ไม่ backward-compatible — redeploy image เก่า ย้อนไม่ได้ ต้อง restore database เท่านั้น

    Monitoring — ดูอะไรทุกวันช่วงสัปดาห์แรกๆ

    • webhook delivery ที่ fail
    • import ที่มี error row
    • error log
    • response time ช่วง peak รับ specimen ตอนเช้า

    Troubleshooting

    • schema_migrations ค้าง — ไฟล์ migration ล้มกลางทาง เช็ค row ที่ไม่ commit แล้วแก้ก่อนรันรอบถัดไป
    • CORS_ORIGIN ไม่ตั้งใน production — fail closed เว้นแต่ตั้ง CORS_ALLOW_ANY=true
    • แก้สิทธิ์ role แล้วไม่มีผล — permission ถูกก็อปปี้ลง JWT ตอน login แล้ว ต้อง logout/login ใหม่

    code name_th level permissions
    super_admin ผู้ดูแลระบบสูงสุด 0 *
    company_admin ผู้ดูแลบริษัท 1 company.*, branch.*, user.*, patient.*, lab.*, report.*, billing.*, settings.*
    branch_admin ผู้ดูแลสาขา 2 branch.view, user.*, patient.*, lab.*, report.*, billing.*

    matching: ฝั่งที่ได้รับสิทธิ์รองรับ wildcard (*, lab.*, lab.result.*) ฝั่งที่ต้องมีสิทธิ์ต้องเป็น leaf เจาะจงเสมอ. user ถือ role เดียว — ไม่มี join table แบบ multi-role. เข้าถึงได้ต้องมีทั้ง role permission และ company feature entitlement — feature guard short-circuit ให้ super_admin เสมอ

    Env var ที่เปลี่ยนพฤติกรรมเมื่อไม่ตั้ง

    env var required? default ถ้าไม่ตั้ง
    DATABASE_URL required – boot fail
    DIRECT_DATABASE_URL optional fallback = DATABASE_URL ถ้ามี pooler แบบ transaction-mode: migration พังเงียบๆ
    JWT_SECRET required, ≥32 chars – boot fail
    REDIS_URL optional – ไม่มี token revocation, ไม่มี login lockout, ไม่มี rate limit
    CORS_ORIGIN optional – production: fail closed เว้นแต่ CORS_ALLOW_ANY=true
    PUBLIC_API_RATE_LIMIT_PER_HOUR optional 1000 ใช้ default
    MINIO_ENDPOINT / MINIO_ACCESS_KEY / MINIO_SECRET_KEY optional – ไม่มี attachment
    SMTP_HOST (เมื่อ EMAIL_PROVIDER=smtp) optional – ส่งอีเมลคืน 503 และ log ว่า failed
    FIELD_ENCRYPTION_KEY optional (แต่ required ใน production จริง), 64 hex chars – PII (เลขบัตร ปชช., เลขกรมธรรม์) ไม่ encrypt
    SCHEDULER_ENABLED optional true ปิดตลอดถ้ารันบน Vercel (มี env VERCEL)
    HANDOFF_PRIVATE_KEY optional – SSO handoff endpoint คืน 503
    TELEGRAM_BOT_TOKEN optional – แจ้งเตือนผ่าน telegram บันทึกเป็น "skipped"

    สิ่งที่ระบบยังไม่มี

    • inbound HL7 (ไม่มี ORU parser, ไม่มี MLLP listener, ไม่มี ACK handling)
    • import แบบ CSV/XML/fixed-width — รับ .xlsx เท่านั้น
    • import สำหรับแผนก, ชนิดสิ่งส่งตรวจ, หน่วยงานส่งตรวจ, ค่าอ้างอิง, กลุ่มลูกค้า
    • ตาราง LOINC หรือ ICD — ทั้งสองเป็นช่องข้อความอิสระ ไม่ validate
    • import ผลตรวจย้อนหลัง (historical results)
    • background job queue สำหรับ import
    • คำสั่ง bootstrap สร้าง super_admin คนแรก
    จบเล่ม — กด Ctrl+P เพื่อพิมพ์ทั้งเล่ม
